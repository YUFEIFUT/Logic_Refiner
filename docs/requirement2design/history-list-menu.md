# 需求：历史记录列表操作菜单——统合删除与新增重命名

## 背景

### 现状

当前历史记录列表中，每个记录项右侧 hover 时显示一个删除按钮（Trash2 图标），点击后弹出确认对话框。这种方式存在两个问题：

1. **功能扩展性差**：删除按钮独占了 hover 区域，后续想加其他操作（如重命名）没有空间
2. **操作不直观**：用户需要 hover 才能看到删除按钮，且图标较小（3x3），不够醒目

### 参考设计

参考 DeepSeek 网页端的设计：每个记录项右侧有一个 "..." 按钮，点击后弹出下拉菜单，菜单中包含"重命名"和"删除"两个选项。这种设计统合了所有操作入口，后续扩展新功能也只需在菜单中加一项。

### 用户需求

- 支持**重命名**：用户可以修改历史记录的 input（即该记录的标题/命题）
- 支持**删除**：保留现有删除功能，但从 hover 按钮移入菜单中

---

## 设计原则

| 原则 | 含义 |
|------|------|
| **操作入口统一** | 所有记录级操作（重命名、删除）通过同一个 "..." 菜单触发 |
| **渐进式展示** | 默认隐藏操作菜单，hover 显示 "..." 按钮，点击展开菜单 |
| **破坏性操作确认** | 删除需要二次确认，重命名不需要（可随时改回） |

---

## 子任务

### 3.1 后端：新增重命名 API

**目标**：新增一个 API 端点，支持修改记录的 `input` 字段。

**修改位置**：`server.ts`（新增端点）+ `src/db.ts`（新增函数）

**设计**：

- **端点**：`PUT /api/refinements/:id/input`
- **请求体**：`{ "input": "新的标题文本" }`
- **校验**：input 必须为非空字符串【在前端和后端都进行校验，前端校验后端校验，防止前端绕过校验提交空字符串。前端校验是整个内容不能是纯粹的空白符，后端的话，拿到内容进行trim操作，然后再判断是否为空字符串】
- **数据库**：`db.ts` 新增 `updateRefinementInput(db, id, input)` 函数，执行 `UPDATE refinements SET input = ? WHERE id = ?`

选择独立端点而非复用现有 `PUT /api/refinements/:id`，因为后者用于更新 finalLogic/explanation/stages，职责不同，避免互相干扰。

**验收标准**：
- [x] `db.ts` 新增 `updateRefinementInput` 函数
- [x] `server.ts` 新增 `PUT /api/refinements/:id/input` 端点
- [x] 端点校验 input 非空
- [x] 端点校验 id 有效且记录存在
- [x] 成功时返回 `{ success: true }`
- [x] 失败时返回 400（参数错误）或 404（记录不存在）

### 3.2 前端：用下拉菜单替换 hover 删除按钮

**目标**：将每个记录项右侧的 hover 删除按钮替换为 "..." 按钮 + 下拉菜单，菜单包含"重命名"和"删除"两个选项。

**修改位置**：`src/components/HistoryList.tsx`

**设计**：

1. **"..." 按钮**：替换原来的 Trash2 按钮，使用 `MoreHorizontal` 图标（lucide-react），hover 时显示
2. **下拉菜单**：点击 "..." 后弹出，绝对定位在按钮下方
   - 菜单项 1：重命名（`Pencil` 图标）
   - 菜单项 2：删除（`Trash2` 图标，红色文字）
3. **菜单行为**：
   - 点击菜单外部或选择菜单项后关闭
   - 点击"删除"→ 弹出现有的删除确认对话框
   - 点击"重命名"→ 进入内联编辑模式
4. **状态管理**：新增 `menuOpenId` state 记录当前展开菜单的记录 id

**验收标准**：
- [x] 每个记录项 hover 时显示 "..." 按钮（`MoreHorizontal` 图标）
- [x] 点击 "..." 弹出下拉菜单，包含"重命名"和"删除"两个选项
- [x] 菜单点击外部自动关闭
- [x] 点击"删除"走现有确认对话框流程
- [x] 点击"重命名"进入内联编辑模式（菜单项已就位，编辑逻辑待 3.3 实现）
- [x] 原有的 hover Trash2 按钮已移除

### 3.3 前端：实现内联重命名编辑

**目标**：点击"重命名"后，记录的 input 文本变为可编辑的输入框，支持保存和取消。

**修改位置**：`src/components/HistoryList.tsx`

**设计**：

1. **进入编辑**：点击"重命名"后，菜单关闭，记录项的 input 文本替换为 `<input>` 元素
   - 新增 `editingId` state 记录当前编辑中的记录 id
   - 新增 `editingValue` state 存储编辑中的文本
2. **输入框行为**：
   - 自动聚焦并全选文本
   - 按 Enter 或点击"保存"按钮 → 保存
   - 按 Escape 或点击"取消"按钮 → 取消编辑
   - 文本为空时禁用保存按钮
3. **保存**：调用 `PUT /api/refinements/:id/input`，成功后刷新列表并显示 toast
4. **取消**：恢复原始 input，退出编辑模式
5. **同时选中的记录**：如果正在编辑的记录被选中（`selectedId`），保存后需要通知父组件刷新选中记录的数据（因为 input 变了）

**验收标准**：
- [x] 点击"重命名"后，记录项 input 变为输入框
- [x] 输入框自动聚焦，内容全选
- [x] Enter 保存，Escape 取消
- [x] 空文本时保存按钮禁用
- [x] 保存成功后列表刷新，显示新名称
- [x] 保存成功后显示 toast 提示
- [x] 保存失败时显示错误 toast，不退出编辑模式

### 3.4 前端：重命名后刷新选中记录

**目标**：当用户重命名了当前选中的记录时，父组件（App.tsx）中展示的 input 标题也需要同步更新。

**修改位置**：`src/App.tsx`（可能无需修改，需验证）

**设计**：

当前 `HistoryList` 的 `onSelect` 回调接收完整 `HistoryRecord` 对象。保存重命名后，可以通过以下方式同步：
- 方案 A：保存后调用 `onRefresh?.()` 让父组件自行刷新
- 方案 B：新增 `onRename(id, newInput)` 回调，父组件直接更新 state

推荐方案 A，因为当前已有 `onRefresh` 机制，无需新增接口。验证 `onRefresh` 是否已能触发父组件重新加载选中记录即可。

**验收标准**：
- [x] 重命名选中的记录后，页面顶部/正文中的标题同步更新
- [x] 无需手动刷新页面
